# Deploy to Render

`render.yaml` at the repository root is a [Render Blueprint][blueprint]. It creates:

- **`xolotl`**, a Docker web service built from this repository's `Dockerfile`: the API,
  the staff console (served at `/`) and the embedded worker, in one container, with a
  1 GB persistent disk at `/var/data` for the object store.
- **`xolotl-db`**, a Render Postgres 17 database (user `xolotl`, database `xolotl`).

Both run in `oregon`, on the smallest paid plans (see [Costs](#costs)). The one value you
paste is `XOLOTL_MASTER_KEY`; Render generates the rest or reads them from the database.

## Before you start

1. **The repository on GitHub.** The Blueprint tracks `main` of
   [github.com/OmarIbannez/xolotl](https://github.com/OmarIbannez/xolotl), where this
   guide lives. Merge the pull requests in order and wait for CI to pass on `main` before
   you create the Blueprint: the CI workflow runs on pushes to `main`, and the service
   deploys a commit only after its checks pass (`autoDeployTrigger: checksPass`). Render
   skips a commit on which no check ran, so a branch CI does not run on would never
   deploy.
2. **A Render account** with GitHub connected and access to that repository, and a payment
   method: the plans are paid. A Hobby workspace is enough.
3. **The master key.** Make it on your machine and store it in your password manager
   before you go on:

   ```bash
   openssl rand -base64 32
   ```

   It wraps every tenant's data keys. Render keeps it as an environment variable, but keep
   your own copy: if the service is deleted or the variable is changed, everything that
   was encrypted can no longer be read, and there is no master-key rotation yet. It is
   pasted rather than generated by Render for that reason.

## Create the Blueprint

1. In the Render Dashboard, click **New > Blueprint** and pick the repository and the
   `main` branch.
2. Render reads `render.yaml` and lists the service and the database. It asks for one
   value, `XOLOTL_MASTER_KEY`: paste the key (44 characters, ending in `=`).
3. Click **Deploy Blueprint**.

## What the first deploy does

Render creates the database, generates `XOLOTL_JWT_SECRET` and `XOLOTL_APP_DB_PASSWORD`
(base64 of 256 random bits each), builds the image (the console, then the Python
dependencies; several minutes), mounts the disk and starts the image's command,
`xolotl serve`, which:

1. **Reads the configuration.** `XOLOTL_ENV=prod` refuses the development JWT secret and
   master key. Render hands over the database owner's URL only
   (`XOLOTL_DATABASE_ADMIN_URL`, a `postgresql://` URL on the private network), so the
   application's URL is derived from it: the same database, signing in as `xolotl_app`
   with `XOLOTL_APP_DB_PASSWORD`.
2. **Bootstraps the app role.** `xolotl_app` cannot sign in, because it does not exist
   yet, so `serve` runs what `xolotl db bootstrap` runs, as the owner: it creates the
   role with `LOGIN NOSUPERUSER NOBYPASSRLS NOCREATEDB` and the generated password,
   grants it `CONNECT` on the database and `USAGE` on the `public` schema (the
   migrations grant the tables), and checks that it cannot bypass row-level security.
   The password travels as a SCRAM-SHA-256 verifier computed by libpq on the
   application's side, so an `ALTER ROLE` the server refuses and logs carries the
   verifier and never the password. The log says
   `app role cannot sign in; bootstrapping it`. Render's default database user is not a
   superuser; Render's documentation implies it may create roles, which is all
   bootstrap needs (see [the database role](#the-database-role) below). `serve`
   refuses to bootstrap when `XOLOTL_APP_DB_PASSWORD` (or `XOLOTL_DATABASE_URL`) is
   missing, so the role is never created with the development password.
3. **Migrates** to the latest revision and creates the audit partitions for this month and
   the next three.
4. **Checks the app role** as the application signs in: a role that is a superuser or has
   `BYPASSRLS` stops the start with exit status 1.
5. **Reports the disk**: `object store root is writable`, or a warning (see
   [Disk permissions](#disk-permissions)).
6. **Serves** on the port Render sets (`PORT`, 10000) and starts the worker thread
   (events, jobs, schedules).

Render then calls `GET /readyz`, which signs in as the app role; on `200` the deploy is
live at `https://xolotl.onrender.com` (Render adds a suffix if the name is taken).

Every later start repeats these steps. The role is left alone while it signs in; when
you change `XOLOTL_APP_DB_PASSWORD` in the dashboard, the next start finds the old
password refused and runs bootstrap again, which sets the new one. The environment is
the source of truth: rotate the password by editing the variable, not in the database.
A lock-out done in the database (`ALTER ROLE xolotl_app NOLOGIN`, or a new password set
with `psql`) is undone by the next start, which puts the variable's value back. To cut
the application off, suspend the service.

## Create the first tenant

Open the service's **Shell** tab in the Render Dashboard (paid services only) and run:

```bash
xolotl tenant create --slug acme --legal-name "Acme SA de CV" --admin-email admin@acme.mx
```

The shell opens in the running instance as the image's user, `xolotl`. The command
prints the administrator's one-time password once: copy it now. Add `--env PROD` for a
production workspace (the default is `SANDBOX`); `--country` defaults to `MX`.

If the Shell tab does not open (Render lists extra requirements for Docker images, which
the image meets), or the command reports a missing setting, run it from your machine
against the database's external URL instead. The database accepts connections from the
private network only (`ipAllowList: []` in `render.yaml`): first add your address under
**xolotl-db > Access Control** in the dashboard, and remove it when you are done. Use a
directory without a `.env` file, which the CLI would read:

```bash
cd "$(mktemp -d)"
export XOLOTL_ENV=prod
export XOLOTL_DATABASE_ADMIN_URL='<xolotl-db > Connect > External Database URL>?sslmode=require'
export XOLOTL_APP_DB_PASSWORD='<xolotl > Environment > XOLOTL_APP_DB_PASSWORD>'
export XOLOTL_MASTER_KEY='<the master key>'
export XOLOTL_JWT_SECRET="$(openssl rand -base64 32)"  # required by prod, unused here
uv run --project /path/to/xolotl xolotl tenant create --slug acme \
  --legal-name "Acme SA de CV" --admin-email admin@acme.mx
```

A tenant's first keys take the master-key reference of whoever creates them, and keys
wrapped under the wrong master key can be neither mended nor re-wrapped (README, "Master
key"). The Shell path needs no check: it runs under the service's own key. From your
machine the pasted `XOLOTL_MASTER_KEY` can differ from the service's, so compare the two
references before anyone uses the tenant. In the same shell, print yours:

```bash
uv run --project /path/to/xolotl python -c "from xolotl.platform.config import get_settings; from xolotl.platform.crypto.provider import kek_ref_for; print(kek_ref_for(get_settings().master_key_bytes))"
```

Then read the tenant's with `psql` on the same external URL, naming the tenant first
(the id is in the `tenant acme created (...)` line) because `tenant_key` is under forced
row-level security:

```sql
SELECT set_config('app.tenant_id', '<tenant id>', false);
SELECT DISTINCT kek_ref FROM tenant_key;
```

If the two differ, the key you pasted is not the one the service runs with: that slug is
lost (the README says why); fix the key in your shell and create the tenant again under
another slug.

## Sign in

Open the service URL. Sign in with the workspace (`acme`), the email and the one-time
password; the console asks for a new password (at least 12 characters) and opens the
home page. Turn on two-step verification under **Security**. The API documentation is at
`/v1/docs`.

## Check a deploy

- **Logs** show JSON lines; a healthy start has `Uvicorn running on http://0.0.0.0:10000`
  and `embedded worker started`.
- `GET https://<service>.onrender.com/readyz` answers `{"status":"ok","database":"ok"}`.
- `object store root is writable` appears once per start.

## Disk permissions

Render does not document who owns a persistent disk when the image runs as a non-root
user, and reports from other projects say disks mount owned by root. The image's user
(uid 10001) also belongs to group 1000, the group Render documents for the
[secret files][docker-secrets] it mounts at runtime. If the start logs
`object store root is not writable by this process`, nothing fails today, because no
feature writes objects yet, but uploads will. Compare `id` and `ls -ldn /var/data` in the
Shell, then ask Render support how the disk is owned, or have the image start as root to
hand `/var/data/objects` to uid 10001 before it drops to that user.

## The database role

Render's default database user owns the database and the tables the migrations create,
so it cannot be the application's role: row-level security does not bind a table's
owner unless forced, and an owner can lift it. Render's documentation says users created
with `CREATE USER` are not managed by Render ([credentials][pg-credentials]) and
recommends creating a dedicated role for logical replication
([logical replication][pg-replication]), so the default user may create roles; the same
page has the support team run the one statement that needs a superuser. This was not
tried on Render itself; locally, bootstrap succeeds through a non-superuser owner with
`CREATEROLE`. If the first deploy instead logs
`error: could not create role xolotl_app (sqlstate 42501)`, the default user lacks
`CREATEROLE`. Ask Render support for one of two things, then redeploy: grant the default
user `CREATEROLE`, so bootstrap runs as rehearsed; or create `xolotl_app` (`LOGIN`, no
superuser, no `BYPASSRLS`, not a member of the default user) with exactly the value of
`XOLOTL_APP_DB_PASSWORD` from the service's environment, so the sign-in succeeds and
bootstrap never runs. With the second, every later change of that variable needs support
again: setting another role's password takes `CREATEROLE` plus `ADMIN OPTION` on the
role, so `ADMIN OPTION` alone is not enough (the refused `ALTER ROLE`, which the server
logs, carries the password's SCRAM verifier, never the password). Do not point the
application at the owner instead.

Rotating the default user from the database's **Credentials** section is untested: the
new default user must be able to act as the owner of the existing tables for migrations
to run.

## Operating notes

- **One instance.** The disk attaches to one instance, and every instance would run its
  own worker, so the service stays at `numInstances: 1` with no autoscaling. Scaling out
  needs an object store adapter other than the disk and the worker split into a Render
  background worker (`XOLOTL_EMBEDDED_WORKER=false` on the web service, `xolotl worker`
  on the worker).
- **Deploys stop the old instance first.** With a disk, Render stops the running instance
  before it starts the new one ([disks][disks]), so each deploy has a few seconds of
  downtime, and migrations run with no old version serving, which is what migrations
  such as 0004 require. That is why there is no `preDeployCommand`: it would run on a
  separate instance while the old version still serves ([deploys][deploys]).
- **Shutdown.** Render sends `SIGTERM` and waits 30 seconds, a delay a service with a disk
  cannot change. `serve` is the container's main process, so it receives the signal
  itself, finishes in-flight requests and stops the worker after its tick.
- **Health.** `/readyz` checks the database as the app role and answers `503` with
  `embedded worker stopped` when the worker thread has died. If it fails for 60 seconds,
  Render restarts the instance: in this single container, that is how a dead worker
  comes back.
- **Backups.** Paid Postgres plans have point-in-time recovery (3 days on a Hobby
  workspace, 7 on Pro), and the disk gets a daily snapshot kept for at least 7 days. The
  two are not taken together. The master key is in neither, which is the point: keep
  your copy.
- **Master key rotation is not supported in this MVP.** Changing `XOLOTL_MASTER_KEY` makes
  every tenant key unreadable (`503 KEK_MISMATCH`). Keep it stable.
- **Pushes to `main`** redeploy once CI passes. Changes outside the image's inputs (the
  `buildFilter` in `render.yaml`: docs, `render.yaml` itself) do not rebuild it.
- **Fixed at creation:** the region, the Postgres version, the database name and user. To
  serve Mexico with less latency, change both `region: oregon` lines to `ohio` or
  `virginia` before the first sync.
- **External database access** is closed: `ipAllowList: []` under the database in
  `render.yaml` allows only the private network (the service and its Shell), where Render
  would otherwise accept any address with valid credentials. To reach the database from
  your machine, add your address under **xolotl-db > Access Control** for the duration
  and remove it afterwards; the external URL needs `?sslmode=require`.

## Costs

Monthly prices from [render.com/pricing][pricing] on 2026-10-18:

| Item | Plan | Per month |
| --- | --- | --- |
| Web service `xolotl` | `0.5c-512mb` (Starter): 0.5 CPU, 512 MB | $7.00 |
| Disk `objects` | 1 GB at $0.25 per GB | $0.25 |
| Postgres `xolotl-db` | `0.1c-256mb` (Basic-256mb): 0.1 CPU, 256 MB, 100 connections | $6.00 |
| Postgres storage | 5 GB at $0.30 per GB | $1.50 |
| Workspace | Hobby | $0 |
| **Total** | | **$14.75**, plus bandwidth over 5 GB a month ($0.15 per GB) |

The free plans do not fit: a free web service has no persistent disk and no shell and
sleeps after 15 idle minutes, stopping the worker; a free database expires after 30 days
and has no backups ([free plans][free]). The next steps up are `1c-2g` for the web
service ($25: the container idles near 90 MB, and every password check takes about
64 MB) and `0.5c-1g` for Postgres ($19). Disk and database storage can grow without
downtime but never shrink.
