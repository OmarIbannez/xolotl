# Technical research: screening (sanctions / PEP / adverse media) and regulatory-reporting formats

**Date:** 2026-10-17 (probes ran 2026-10-17/18 UTC)
**Scope:** A multi-tenant KYC/AML SaaS for LATAM fintechs. Launch in MX, then BR, CO, AR, CL, PE, later EC, UY, PA, DO.
**Stack assumed:** Python (FastAPI, Pydantic), Postgres, OpenSearch, Kafka, Temporal, AWS.
**Evidence tags:**
- **VERIFIED**: fetched or downloaded from the official source during this session (the URL is given).
- **SECONDARY**: reputable third-party source.
- **UNVERIFIED**: inference, or no source could be found.

No prices are invented. Where no public price exists, the cost signal says so.

Related raw files with jurisdiction detail on the regulatory side (not repeated here): `2026-10-17-reporting-mx-br.md`, `2026-10-17-reporting-co-ar-cl-pe.md`, `2026-10-17-reporting-rest-of-latam.md`.

**Cross-cutting LATAM notes**
- In practice, every LATAM regulator expects **UN (binding) + OFAC (de facto, given USD correspondent-banking exposure) + local lists**. EU and UK lists are good practice for fintechs with EU/UK counterparties.
- **Interpol Red Notices** are not distributed in bulk. The public API (`ws-public.interpol.int/notices/v1/red`) only exposes the subset of notices that have been made public. AR RePET embeds selected red notices. (UNVERIFIED for the API in this session.)

### C.2 Recommended own-pipeline design (phase 2, if built)

5. **Risk classification**: an LLM with a strict JSON schema (Pydantic). 6. **Human review UI** with highlighted evidence spans. Keep a feedback loop into a labeled set.

## D. Name matching for Hispanic / Lusophone names

### D.1 Naming conventions that drive design
- **Spanish-speaking (MX, CO, AR, CL, PE, EC, UY, PA, DO):** `given name(s) + paternal surname + maternal surname`. Customers often omit the maternal surname, and lists often give only one surname (OFAC: "GUZMAN LOERA, Joaquin"). AR and UY commonly use only the paternal surname socially. Compound given names (José Luis, María Guadalupe, Juan Pablo) are often abbreviated to one name. Particle surnames: `de la Cruz`, `del Río`, `de los Santos`, `y` joining surnames (`Ortega y Gasset`). Married-name forms: `María López de García`, `Sra. de García`, `viuda de` / `vda. de`. Hyphenated or compound surnames: `Pérez-Reverte`, `Ruiz de Alarcón`, `San Martín`, `Santa Cruz`.
- **Brazil / Portuguese:** `given name(s) + maternal surname(s) + paternal surname`. **The last surname is the family name** (reverse of Spanish), and people are filed by the last surname (Lula da Silva → "SILVA"). Particles `da, de, do, das, dos, e`. Suffixes `Filho, Neto, Júnior/Jr, Sobrinho`. Very long names (4–6 tokens). The CGU file truncates at 60 chars. Women often add the husband's surname at the end.
- **Nicknames and hypocorisms** (must be dictionary-driven): José→Pepe, Chepe (CA), Joselito. Francisco→Paco, Pancho, Curro, Chico (PT). José María→Chema. María Guadalupe→Lupe, Lupita. Jesús→Chucho, Chuy. Ignacio→Nacho. Eduardo→Lalo. Guillermo→Memo. Rosario→Chayo. Concepción→Concha, Conchita. Dolores→Lola. Enrique→Quique. Alfredo→Fredo. Roberto→Beto. Alberto→Beto. Antonio→Toño, Tony. Manuel→Manolo. Luis→Lucho. Consuelo→Chelo. Ignácio/Inácio→Nacho (PT). PT: José→Zé, Antônio→Tonho, Sebastião→Tião, Francisco→Chico, Raimundo→Mundinho. **The rigour/OpenSanctions name DB is incomplete here (Pepe is not linked to José; VERIFIED).**
- **Transliteration/orthography:** accent loss (García/GARCIA), `ñ` → `n`/`nh`/`ny`, BR `ç` → `c`, older orthographies (Ignacio/Ygnacio, Xavier/Javier, Ximénez/Jiménez), seseo (`z/c` ≈ `s` throughout LATAM), yeísmo (`ll` ≈ `y`), b/v merger, silent `h`. Arabic/Lebanese and Asian names are common in LATAM (Slim, Fujimori), so do not over-fit Hispanic rules: apply the language-specific rules **as extra variants**, not replacements.

**Conclusions**
- Off-the-shelf Spanish phonetics are **Castilian-centric** (no seseo in Spanish Metaphone) and miss the `h`-drop and `x/j`. Published research: Amón, Moreno and Echeverri compared Spanish encoders for record linkage and found "Phonetic Spanish" performed best most of the time ([SciTePress 2016](https://www.scitepress.org/PublishedPapers/2016/62277/62277.pdf); [modified Spanish Phonetic vs Soundex/Phonex](https://www.researchgate.net/publication/285589803_Comparison_of_a_Modified_Spanish_Phonetic_Soundex_and_Phonex_coding_functions_during_data_matching_process)). SECONDARY.
- BR: **metaphonebr** (Ipea, MIT, R package v0.0.5) is an adapted Metaphone-BR for Brazilian names. It keeps final vowels as a gender signal ([CRAN](https://cran.r-project.org/web/packages/metaphonebr/index.html)). abydos has `SoundexBR`. Neither has an independent benchmark.
- abydos is **unmaintained** (0.5.0 is the last release), so do not depend on it at runtime.
- **Recommendation: implement our own small "LATAM phonetic key"** (about 40 regex rules; port ideas from PhoneticSpanish and metaphonebr) and unit-test it against a pair corpus:
  - ES rules: `h` silent (except `ch`); `ll|y → Y`; `v → B`; `z|ce|ci → S`; `qu|k|c[aou] → K`; `gu[ei] → G`; `g[ei]|j|x(before vowel, word-initial MX) → J`; `ñ → NY`; `sh → X`; `tz|tl` kept (Nahuatl); `rr → R`; collapse doubles; drop final `s/z` *only in the fuzzy key*.
  - PT rules: `ç|ss|sc[ei]|xc → S`; `ch|sh|x → X`; `lh → LI`; `nh → NI`; `ph → F`; `th → T`; `w → V`; `y → I`; `k → K`; final `m → N`; final `ão|am → AUN`; `qu → K`.
  - Use the phonetic key **only for candidate retrieval (blocking) and as one scoring feature**, never as the sole match criterion.

### D.3 Recommended normalization pipeline (applied identically to list entries and queries)
1. Unicode **NFKC**, then casefold, then **NFKD and strip combining marks** (accent folding). Keep the original string for display and audit. Map `ñ → n` in the folded form, and add an `ny` variant only in the phonetic key. Map `ç → c`, `ß → ss`, `ø → o`.
2. Strip punctuation except intra-name hyphens and apostrophes. Then split hyphens into a joined token plus separate tokens (both variants).
3. **Honorific/title removal** (sr, sra, srta, don, doña, dr, dra, lic, ing, arq, mtro, gral, cnel, sr., sra., dom, dona, sr(a)., "el", "la" when prefix…), from a data file (start from `rigour` PERSON_NAME_PREFIXES plus LATAM additions).
4. **Particle handling**: tag `de, del, de la, de las, de los, da, das, do, dos, y, e, van, von, di, du, la, las, los, san, santa` as *particles*. Never drop them from the display form. Exclude them from token-similarity denominators. Glue them to the following token for a "compound surname" variant (`de la cruz → delacruz`). Also generate a variant without particles.
5. **Generational/suffix tokens**: `jr, junior, júnior, filho, neto, sobrinho, segundo, ii, iii`. Keep them as a *qualifier feature* (mismatch = soft penalty), not as name tokens.
6. **Married-name patterns**: `X de Y`, `X vda de Y`, `X viuda de Y` → generate variants `X` and `Y` (husband's surname) and flag `married_name_variant`.
7. **Structure parsing** (when the input is structured: given/paternal/maternal), with a country hint from the document or nationality:
   - ES order: `G1 [G2] P M` → variants: `G1 P`, `G1 P M`, `G1 G2 P`, `G2 P` (people often go by the second given name, e.g. "María Guadalupe" → "Guadalupe"), `P M G1` (list order "SURNAME, Given").
   - BR order: `G1 [G2] [M…] P` → the family-name slot is the **last non-suffix token**. Variants: `G1 P`, `G1 Mlast P`, `P, G1`.
   - Unstructured strings (most list entries): treat the tokens as an **unordered bag**, with a family-name weight learned per list (`nm_family_name_weight 1.3` in logic-v2).
8. **Nickname expansion**: dictionary `hypocorism → canonical given name(s)` (ES/PT, ~500 entries, seeded from the list in D.1 plus Wikidata "diminutive of" (P1449 / "nickname of")). Expand at **query time** (cheaper) into alternative given-name tokens, with a small penalty (score × 0.95).
9. **Common-surname IDF**: compute token frequencies over the national population or customer base (INE/IBGE surname frequencies or our own tenant-aggregate statistics). Weight = `log(N / df)`, capped. García, Hernández, Martínez, López, González, Rodríguez, Pérez, Sánchez, **Silva, Santos, Oliveira, Souza, Pereira, Lima** get low weight. This is the single biggest FP reducer for LATAM.

### D.4 Similarity scoring
- **Token alignment**: for person names, compute a **Monge-Elkan-style best alignment**. Each query token is matched to its best candidate token with an inner similarity `sim(t1, t2) = max(JaroWinkler(t1, t2) [p=0.1, prefix ≤4], 1.0 if phonetic_key equal and len ≥ 3 else 0, 0.9 if initial-vs-full-name match (J. ↔ José), 0.92 if nickname-equivalent)`. Each aligned pair is weighted by `IDF(token) × role_weight` (family-name role weight 1.3, given 1.0, particle 0, suffix 0). Use a Hungarian or greedy assignment (rapidfuzz `process.cdist` for speed).
- **Asymmetric penalties for unmatched tokens**, as in logic-v2: unmatched *query* tokens weigh 0.8 (the customer gave a name part the list lacks, which is suspicious), unmatched *result* tokens weigh 0.2 (lists often have more aliases or parts). This handles "missing maternal surname" gracefully.
- **Whole-string features**: `rapidfuzz.fuzz.token_set_ratio`, `token_sort_ratio`, and the Levenshtein ratio on the glued compact form (handles "DELACRUZ" vs "DE LA CRUZ"). Use these as additional features or as the fallback for organizations.
- **Organizations**: normalize legal forms (`S.A. de C.V.`, `S.A.P.I. de C.V.`, `S. de R.L.`, `SOFOM E.N.R.`, `S.A.S.`, `Ltda.`, `LTDA`, `EIRELI`, `ME`, `EPP`, `S.R.L.`, `S.C.`, `A.C.`, `SpA`) to type tags (rigour `org_types` covers many, so extend it). Remove generic words with low IDF ("comercializadora", "grupo", "servicios", "inversiones", "constructora"). Add a number-mismatch penalty (logic-v2 `nm_number_mismatch 0.3`).

### D.5 Secondary identifiers (decisive in LATAM because national IDs exist)
| Feature | Effect (start values; calibrate) |
|---|---|
| Exact national ID match (**CURP, RFC** with homoclave, **CPF/CNPJ**, **cédula CO/EC/DO**, **DNI/CUIT/CUIL AR**, **RUT CL**, **DNI/RUC PE**, passport no. + country) | **Auto-confirm / score floor 0.95**. A different ID of the *same type and country* gives **−0.5 / auto-discard eligible** (IDs are unique). OFAC SDN often carries RFC/CURP/cédula, so exploit it. |
| Partial/masked ID (BR CGU PEP masked CPF `***.ddd.ddd-**`) | Match the 6 visible digits: +0.25 if equal, −0.4 if different |

| Gender | Mismatch −0.20 (derive from CURP / name-gender model; BR final-vowel heuristic). |

| Address / city | Weak positive +0.05…+0.2 |

### D.6 Proposed scoring formula and thresholds
```
name_score  = Σ_aligned( idf_i · role_i · sim_i ) / ( Σ_query( idf_q · role_q · w_q ) + Σ_result_unmatched( idf_r · role_r · 0.2 ) )
              where w_q = 1 for matched tokens and 0.8 for unmatched query tokens
              (normalized to 0..1; take max over all list aliases; weak aliases × 0.8)
final       = clamp( name_score + Σ qualifiers(D.5), 0, 1 )
              with hard rules: ID match → max(final, 0.95); ID conflict (same type) → min(final, 0.3)
```
- **Three bands, calibrated per list type** (start values, to be set by the evaluation in D.8):
  - Sanctions (UN/OFAC/EU/UK/RePET/LPB): `final ≥ 0.70` → alert (yente default 0.70). Treat `0.55–0.70` as "low-confidence" alerts **only when there are no contradicting qualifiers**. Sanctions favour recall.
  - PEP: alert at `≥ 0.80` (huge lists, so FP cost is high), plus a country-of-office relevance filter.
  - Adverse media: `≥ 0.85` name, **plus** at least one context corroboration (age/city/occupation) from the LLM extraction.
- **Auto-discard rules** (logged, auditable, reversible): an ID conflict, or DOB disjoint by more than 5 years *and* gender mismatch, discards the alert. Always keep the evidence record.
- Each tenant may **tighten** thresholds but not loosen them below a platform floor (regulatory defensibility). Version the scoring config, store it with each decision, and replay on config change.

### D.7 How others do it
- **OpenSanctions / yente:** two-stage. (1) OpenSearch/Elasticsearch candidate retrieval with name keys, phonetic tokens and n-grams. (2) Python scoring (logic-v2 features above; rigour name analysis, family-name weighting, weak alias handling). The training data and weights are public. Thresholds: 0.70 match, 0.50 cutoff. VERIFIED.
- **OFAC Sanctions List Search tool:** whole-string plus per-token Jaro-Winkler-like scores, with a user slider (default ~85). The `ofac` yente algorithm emulates it. Treat it as a **regulator-recognizable baseline** to report alongside our score. SECONDARY.
- **OpenSearch building blocks** (for our own index): `analysis-icu` (`icu_normalizer` nfkc_cf, `icu_folding` for accent folding), `analysis-phonetic` plugin (`phonetic` filter: `double_metaphone`, `beider_morse` with `languageset: ["spanish","portuguese"]`, `daitch_mokotoff`). The Beider-Morse rule set does include Spanish and Portuguese (UNVERIFIED in-session). `fuzzy` / `match` with `fuzziness: AUTO` (Levenshtein ≤2) on folded tokens. **Use OpenSearch only for recall** (top-k ≈ 50–100 candidates per query, `minimum_should_match` on rare tokens). Do the precision scoring in Python (rapidfuzz). Amazon OpenSearch Service pre-installs ICU Analysis and Phonetic Analysis on all domains (OpenSearch ≥1.0), and Serverless also ships them. SECONDARY ([AWS docs](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/supported-plugins.html)).
- **Commercial engines** (World-Check One, Bridger XG, ComplyAdvantage, Ripjar, Castellum): a culture-aware name parser plus a name-variant DB (e.g. "name culture" classification as in IBM InfoSphere Global Name Recognition / Rosette Name Indexer), plus secondary-ID qualifiers, plus ML/LLM-based alert triage. Babel Street (Rosette) Match is the best-known licensable name-matching engine with Spanish/Portuguese name models (SDK, quote-only). UNVERIFIED (no docs fetched).

### D.8 False-positive benchmarks (published)
- **Federal Reserve FEDS working paper (Allen & Hatfield, Oct-2025)**: across realistic thresholds, LLMs cut false positives **by 92%** relative to the best fuzzy-matching baseline and raised detection by **11%**, but ran more than **4 orders of magnitude slower**. Implication: use an LLM **only as an alert-triage layer** on the small post-threshold set, never as the matcher. SECONDARY ([FRB](https://www.federalreserve.gov/econres/feds/can-llms-improve-sanctions-screening-in-the-financial-system-evidence-from-a-fuzzy-matching-assessment.htm)).
- **Finansinspektionen (Sweden) 2024 test** of 19 banks with 5,000 UN/EU names: **97.2% average detection on correctly-spelled names only**. Performance on variants was lower and undisclosed. SECONDARY.
- The common industry claim of "85–95%+ of alerts are false positives" is vendor marketing with no primary study found. **No published LATAM-specific benchmark found** (gap).

### D.9 Evaluation methodology
1. **Labeled corpus** (target ≥ 20k pairs, versioned in S3/Postgres):
   - Positives: the list entries themselves and their aliases. **Synthetic perturbations** generated by rule (drop the maternal surname, swap order, accent loss, seseo/b-v/ll-y substitutions, nickname substitution, initials, particle drop/glue, typo at Levenshtein 1–2, BR order inversions, truncation at 60 chars). Real hits from vendor or tenant historical alert dispositions (with consent).
   - Hard negatives: **homonyms** (same common surnames, different people). Sample from the BR PEP file vs CEIS, and from the CO SIGEP vs RePET. Different DOB/ID pairs. Organizations with shared generic words.
   - Include the **OpenSanctions matcher training data** (public) as an additional benchmark.
2. **Metrics**: precision, recall and F2 (recall-weighted for sanctions) at each threshold. **Recall at a fixed alert budget** (alerts per 1,000 screened customers). PR curves per list type, per country, per name culture (ES vs PT vs other). Latency p95.
3. **Regulatory-style "sample testing"** (as in FI Sweden / Wolfsberg-style model validation): a quarterly blind test set of 500 list names plus variants. Track detection by perturbation type and catch regressions in CI.
4. **Threshold selection**: pick the operating point where sanctions recall is ≥ 0.98 on perturbation classes ≤ "moderate". Report the alert rate on a production-like customer sample (sampled from a tenant with permission, or from a synthetic population generated from INE/IBGE name frequencies).
5. **Champion/challenger**: run yente logic-v2 (baseline), our pipeline, and the OFAC-emulation in parallel in shadow mode. Compare alert overlap and analyst dispositions.

## E. goAML technical details

### E.1 What goAML is
- goAML is UNODC's FIU software (Information Technology Service). It has a reporting front-end (**goAML Web**) and FIU analysis back-end. The **International User Group has 75 FIUs** (FIU-Netherlands). Other estimates say "more than 50" or "more than 70". SECONDARY ([FIU-NL](https://bes.fiu-nederland.nl/en/home/news/), [Fenergo](https://www.fenergo.com/blogs/why-goaml-is-changing-aml-and-sars)).
- **Submission modes** (generic and DR manual, VERIFIED):
  1. **Web forms** on the goAML Web portal.
  2. **XML upload** ("Carga XML") of files that follow the FIU's XSD. Single XML or zip. A **"Validador de Reportes XML"** tab gives a dry-run.
  3. **Message board** (secure mail) with attachments (.doc, .docx, .xml, .png, .jpg, .pdf, .xls, .xlsx, .rtf).
  - **There is no public REST API for reporting entities.** Automation means generating schema-valid XML and uploading it, either by a human or through browser automation (check the FIU's terms first). Some FIUs offer a web-service upload for big reporters (e.g. the goAML "web transactions upload" spec published by MROS Switzerland), but this is per-FIU. UNVERIFIED for any LATAM FIU.

### E.2 Schema: current version and structure (VERIFIED, Luxembourg CRF XSD `xsd-goaml-2026-09-14.xsd`, used as the reference profile)

## Recommended matching pipeline (concrete parameters)

1. **Input normalization** (D.3): NFKC → casefold → accent fold. Honorific strip. Particle tagging. Suffix extraction. Married-name variants. Structure-aware variants (ES vs BR order, chosen by nationality, document type and country hint). Nickname expansion (penalty 0.95). Compute the **LATAM phonetic key** (D.2) per token.
2. **Candidate retrieval (OpenSearch)**: index fields:
   - `name.folded` (ICU tokenizer + `icu_folding` + custom particle stop filter)
   - `name.phonetic_latam` (precomputed keys as a keyword array)
   - `name.bm` (`phonetic` filter `beider_morse`, `rule_type: approx`, `languageset: [spanish, portuguese]`)
   - `name.ngram` (edge 3-grams of compact form)
   - `ids.*` (keyword, normalized: CURP/RFC/CPF/CNPJ/cédula/DNI/RUT stripped of punctuation)
   - `dob_year`, `countries`, `schema`, `topics`, `dataset`, `tenant_id` (for private lists)

   Query: `bool.should` with an exact ID term (boost 10), `match name.folded {fuzziness: AUTO, prefix_length: 1, operator: or, minimum_should_match: "2<70%"}`, `terms name.phonetic_latam`, `match name.bm`. Filter on `schema` and tenant visibility. **top_k = 50** (sanctions) / **25** (PEP). Target retrieval recall ≥ 0.995 on the eval set before tuning scoring.
3. **Scoring (Python, rapidfuzz)**: D.4–D.6 formula. JW prefix scale 0.1. Inner token threshold: a token pair counts as matched if `sim ≥ 0.88`, or the phonetic key is equal (len ≥ 3), or there is an initial/nickname match. IDF from tenant-population + national name frequencies (cap 0.25–3.0). Role weights: family 1.3, given 1.0, particle 0, suffix 0 (suffix mismatch −0.05). Unmatched query-token weight 0.8, unmatched result-token weight 0.2. Weak alias × 0.8. Qualifiers as in D.5. **Run yente `logic-v2` in parallel as a second opinion** (alert if either ≥ threshold during shadow mode, then calibrate).
4. **Decision bands**: sanctions alert ≥ 0.70 (review band 0.55–0.70 without contradicting qualifiers). PEP ≥ 0.80. Adverse media ≥ 0.85 + context. ID match → 0.95 floor (auto-escalate). Same-type ID conflict → cap 0.30 (auto-discard eligible, logged).
5. **Alert triage assist** (post-threshold only): an LLM produces a structured explanation (matched tokens, qualifier agreement, suggested disposition plus rationale) for the analyst. It **never auto-closes sanctions alerts** in v1. Measure the analyst agreement rate before enabling any auto-discard. This follows the Fed paper finding (big FP reduction, but far too slow to run as the primary matcher).
